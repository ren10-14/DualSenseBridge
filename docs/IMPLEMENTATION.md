# ЭТАП 4 — Реализация

Полная реализация моста (код: `src/`). Ключевые сценарии описаны ниже.

## Жизненный цикл приложения

1. **Запуск** (`Program.cs`): разбор CLI. Без флагов — GUI-режим (`TrayApplicationContext`):
   автозапуск моста при готовности зависимостей, иначе — подсказка `--install-deps`.
2. **Проверка/установка драйверов** (`Setup/DriverSetup.cs`):
   - usbip-win2: наличие по реестру/сервису `usbip2_ude`;
   - viiper.exe: поиск в `%LOCALAPPDATA%\VIIPER`, `ProgramFiles\DS4Windows\VIIPER`, рядом с exe;
     запуск без UAC (если найден), иначе — установка с повышением прав
     (`/VERYSILENT /NORESTART`, тихий `/S`, в крайнем случае интерактивно);
   - HidHide: статус сервиса.
3. **Скрытие физического контроллера** (`HidHideManager`): блокировка instance ID DualSense
   для всех процессов, кроме нашего exe (список исключений ApplicationPaths).
   Отмена — `--unhide-device` или при выходе.
4. **Мост** (`BridgeService.StartAsync`):
   - ping VIIPER (:3242) → создать шину → `add {"type":"dualsensegamepadv5"}`;
   - открыть стрим в течение 5 с (handshake `bus/{id}/{devId}\0`);
   - attach физического DualSense (BT в приоритете): открытие, чтение feature 0x05
     (переводит контроллер из минимального режима 0x01 в полный 0x31), сброс подсветки
     (LIGHT_OUT — без него контроллер не даёт программировать цвет после BT-подключения);
   - InputLoop: чтение (BT 0x31 с проверкой CRC / минимальные 0x01) → `DualSenseState` →
     `InputMapper` → `ViiperDeviceStream.SendInputAsync` (кадр 0x01, 33 Б);
   - OnFeedback: кадр 0x81 (474 Б) → `DualSenseFeedback` → `FeedbackTranslator`
     (Native: общий блок из нативного USB-отчёта 0x02 игры + патчи) → `BluetoothHidWriter`.
5. **Реконнекты**: монитор HID-устройств (антидребезг 500 мс) — при отключении DualSense
   мост ждёт повторного подключения; при падении стрима VIIPER — пересоздание устройства.
   Выход: снятие устройства с шины, раскрытие HidHide.

## Патчи безопасности (обязательные по итогам исследования)

| Патч | Причина |
|---|---|
| Триггеры: режимы 0xFC/0xFD/0xFE → Off | отладочные режимы «ломают» привод до сброса (Nielk1) |
| Триггеры: «простые» режимы не используются | 0x01/0x02/0x06 — остаточные, поведение не определено |
| Бит HAPTICS_SELECT (0x02) добавляется, если игра задала моторы без него | hid-playstation.c: rumble всегда 0x01\|0x02, без 0x02 прошивка может игнорировать |
| USB-отчёт ровно 48 Б, BT — 78 Б | Windows отклоняет отчёты длиннее дескрипторных |
| Тег 0x10 и инкремент seq в каждом BT-отчёте | обязательны (hid-playstation.c) |
| Проверка CRC входящих BT-отчётов | защита от повреждённых пакетов радиоволнами |

## Оптимизация пакетов (без обрезки протокола)

- **newest-wins**: в любой момент в очереди не более одного отчёта — при частоте эффектов
  выше пропускной способности BT отправляется самое свежее состояние (для отдачи
  «состояние» важнее истории).
- **Дедупликация**: подряд идущие одинаковые отчёты не пишутся (счётчик SuppressedDuplicates).
- **Минимальный интервал 4 мс** (настраивается 1..100 мс) — период опроса BT.
- **Keep-alive 30 с**: повтор последнего отчёта, чтобы контроллер не «забыл» состояние.
- Никакого обрезания байтов: содержимое протокола всегда полное (47 Б общий блок).

## Диагностика

- Лог: файл (`--log-file`, по умолчанию `%APPDATA%\DualSenseBridge\log.txt`) + событие в UI.
- `--verbose` — отладочный уровень; `--list-devices` — HID-энумерация с метками.
- Тесты эффектов: CLI (`--test-rumble/--test-triggers/--test-led`) и кнопки в окне —
  отправка напрямую в физический контроллер (мост не требуется).
- Окно: статусы VIIPER/виртуального устройства/физического контроллера/батареи/HidHide,
  статистика пакетов (байт в/из, дубликаты, задержка, средний интервал), журнал,
  настройки (режим трансляции, диалект, интервал записи, масштаб вибрации) — применяются
  сразу, сохраняются в `%APPDATA%\DualSenseBridge\settings.json`.

## Ограничения реализации (честно)

- Аудио-путь (PCM динамика из кадров 0x83 и микрофон 0x02/0x85) не транслируется:
  по BT аудио DualSense идёт через стек Bluetooth A2DP/HFP вне HID — эта часть
  остаётся как future work `[НЕ ПОДТВЕРЖДЕНО: возможность проброса PCM через 0x36-носитель]`.
- IMU передаётся «как есть»: единицы физического и виртуального устройств совпадают
  (подтверждено константами VIIPER), но калибровка конкретного экземпляра не переносится.
- Тесты эффектов по USB-подключению тоже работают (WriteCommon использует 0x02/48 Б).

### v1.12.0 — ЗВУК ДИНАМИКА: мост сам кодирует Opus (главный фикс щелчков) + UI

**Найдена настоящая причина «грязного звука»**: viiper V5 НЕ кодирует звук
динамика — носитель 0x36 уходит с ПУСТОЙ Opus-дорожкой («Packet 0x13 … It is
explicitly empty here»), а звук едет ОТДЕЛЬНЫМ хвостом кадра 0x83: ровно
1920 Б raw PCM (480 кадров S16LE стерео 48 кГц = 10 мс). Кодировать дорожку
обязан мост — так делает DS4Windows («DS4Windows injects its already-encoded
200-byte Opus frame before forwarding», docs: «the physical-controller bridge
supplies the encoded speaker lane»). Наш мост хвост ВЫБРАСЫВАЛ — значит,
весь «звук», который слышал пользователь, шёл через АКТУАТОРЫ (Windows
дублирует стерео в задние 4-канальные каналы виртуального устройства) —
отсюда вечные «хрипы/щелчки/жужжание» на любом качестве доставки.

Что сделано:

1. **SpeakerOpusEncoder** (`Output/SpeakerOpusEncoder.cs`, Concentus 2.2.2 —
   чистый C# Opus): 48 кГц стерео, OPUS_APPLICATION_AUDIO, 160 кбит/с CBR,
   Complexity 0, кадр 480 сэмплов → РОВНО 200 Б (короткие кадры отбрасываются —
   «changes its Opus packet structure and can make the controller reject the
   combined report»); дорожка вписывается в носитель: [142]=0x93, [143]=200,
   [144..343]=Opus, глубина медиабуфера [5..9]=0x80 («clean Windows speaker
   traces keep every 0x36 media-lane depth at 0x80»). Контракт 1:1 с
   «exact proven MeasuredTransport DualSense speaker encoder» DS4Windows.
2. **ViiperClient** больше не выбрасывает PCM-хвост 0x83
   (DualSenseFeedback.TryParseAtomic: LE16 + 474 + 1920 → SpeakerPcm).
3. **BridgeService**: PCM → Opus → дорожка носителя ДО постановки в очередь.
4. **Выбор дорожек переписан**: 0x83 — ОСНОВНОЙ медиапоток (динамик+состояние+
   хаптики, 100 Гц), пишется ВСЕГДА. Старое правило «пропускать 0x83, пока
   идут 0x84 (500 мс)» РЕЗАЛО ЗВУК при любой хаптик-активности — это и были
   щелчки. 0x84 — запасной поток только когда аудиокадров нет >150 мс
   (аудиоинтерфейс закрыт): его интервал хаптик дублирует следующий 0x83.
5. **«Немой» блок** больше не повторяет последний кадр динамика («an old Opus
   frame cannot be replayed») — TLV динамика убирается целиком.
6. **UI**: кнопка «Цвет подсветки…» + квадрат-превью прямо в потоке настроек
   (раньше группа настроек была обрезана по высоте — Height 96 → 168, окно
   920×780); окно «Статус и настройки» открывается СРАЗУ при запуске exe.

Тесты: 151/151 (+5: разбор PCM-хвоста, точный 200-Б CBR-кадр в дорожке,
тишина кодируется, неверная длина отклоняется).

### v1.11.0 — «жужжание» вибрации: мост zero-fill дорожки хаптик + выбор цвета подсветки

**Причина жужжания найдена в протоколе viiper** (исходники hbashton/viiper,
device/dualsense/const.go): медиа-кадры 0x83 публикуются на часах 480 кадров
(10 мс, 100 Гц), а интервалы хаптик (rear-каналы игры, 48 кГц) завершаются
каждые 512 кадров (10,667 мс, 93,75 Гц). «Each V5 media frame consumes one
completed rear interval OR ZERO-FILLS that lane» — **каждый ~16-й кадр viiper
присылает дорожку хаптик из НУЛЕЙ** («нового интервала нет»), а не тишину
конца эффекта. Мост проигрывал эти нули актуаторам: сигнал вибрации получал
периодические провалы ⇒ «жужжание/треск» вместо ровной вибрации.

Формат rear-дорожки подтверждён: 64 Б = 32 стерео-пары S8 на 3 кГц — ровно
10,667 мс; кодек контроллера без буфера («no buffer, packets are passed
straight to the audio codec chip» — sdoregor/SAxense), тайминг решает всё.
Viiper готовит дорожку sinc64-ресемплером WDL («sony-bt-wdl-sinc64-v1») —
содержимое аутентичное, портилась только доставка.

**Исправление** (`Output/RearLaneBridge.cs`, включён в пейсер И в синхронный
резерв): нулевые «zero-fill» дорожки мостятся ПОСЛЕДНИМ РЕАЛЬНЫМ блоком
(удержание ≤ 35 мс ≈ 3 блока — по DualSenseRearHapticsUnderrunGate референса
DS4Windows: «Three blocks cover that observed phase»); нули дольше окна
считаются концом эффекта и проходят как есть («The game, not a wall-clock
timeout, owns the end of a native DualSense effect»). «Немой» блок (явное
затухание) не мостится. Статистика: «мост хаптик N/M» (N — замощено, M —
пропущено концов).

**Подсветка — настройка цвета в UI** (v1.11.0): в окне рядом с чекбоксом
«Подсветка по умолчанию» — кнопка «Цвет подсветки…» (системный диалог
цвета) + квадрат-превью; выбор сохраняется в settings.json
(DefaultLightbarColor) и применяется на лету.

Тесты: 146/146 (+5: мост zero-fill, конец эффекта после окна, без истории,
обновление удержания, граница окна).

### v1.10.1 — задержка аудио, «жужжание» вибрации, мерцание подсветки

По скриншоту эксплуатации v1.10.0 (OCR статистики и журнала) выяснено:

1. **Медиа-тракт на машине пользователя НЕ ВКЛЮЧАЛСЯ** — статистика «хаптики:
   записано 359, принято 359» принадлежит старому синхронному писателю (в режиме
   пейсера она была бы нулевой). Причина: создание пейсера стояло за условием
   `dev.Transport == Bluetooth` В МОМЕНТ ВЫБОРА устройства — а транспорт там ещё
   не уточнён классификацией отчётов. Фикс: тракт включается ЛЕНИВО, на первом
   же носителе 0x36 (транспорт уже известен), а режим канала ВИДЕН в статистике:
   «медиа-тракт: асинхронный пейсер…» или «НЕ открыт (Win32 N) — синхронный
   резерв» (+ код ошибки в журнале).
2. **Задержка 85 мс** = стартовый заряд 8 × 10,667 мс. Фикс: заряд 8 → 3 и
   ТОЛЬКО на первый поток соединения (повторные заряды на каждый бурст viiper
   добавляли задержку и «лестницу» вибрации); досрочный слив при очереди
   глубже 4 (очередь сходится к ≤4 ≈ 43 мс без потерь). Ожидаемая задержка
   ~30–45 мс вместо 85; остаток — обязательный запас контроллера на засухи
   завершений Windows BT (39–82 мс), это цена Bluetooth-канала.
3. **«Жужжание вместо вибрации»**: «немой» блок гасил хаптики по таймауту
   45 мс, а viiper delivering бурстами (средний интервал ~63 мс) — эффекты
   рубились на части. Фикс (как в референсе DS4Windows: «The game, not a
   wall-clock timeout, owns the end of a native DualSense effect»): тишина,
   ЯВНО опубликованная игрой (тихий носитель 0x36), гасит хаптики сразу
   (NotifyGameSilence в обоих каналах); таймаут поднят до 250 мс — только
   фолбэк смерти производителя.
4. **Мерцание подсветки**: журнал показал RGB #000000 со скачущими флагами
   (0x42/0x57/0x46) — кадры «флаг управления есть/нет» при чёрном цвете
   переключали подсветку «дефолт ↔ чёрный» на каждом кадре. Фикс: владельцем
   подсветки считается только игра, задающая РЕАЛЬНЫЙ цвет (RGB != 0,
   защёлка на 1,5 с); чёрный с флагом дефолтом подменяется (не мерцает).

Тесты: 141/141 (+4 защёлка цвета, обновлены константы пейсера).

### v1.10.0 — ОТДЕЛЬНЫЙ медиа-тракт 0x36: пейсер 10,667 мс + асинхронные слоты (фикс хрипов/щелчков звука)

Симптом v1.9.9: основной звук игры через контроллер всё ещё идёт с хрипами и
щелканьями (адаптивный темп по EMA не помог). LED игрока и подсветка — работают.

Референс: изучена боевая реализация hbashton/DS4Windows
(DualSenseBluetoothAudioPacer, 8k строк) — единственная, где звук DualSense по
BT работает. Ключевые находки:

1. **Каденция фиксированная: один носитель 0x36 каждые 10,667 мс (93,75 Гц)**
   («one complete speaker/haptics generation per 10.667 ms»). Наш EMA-подход
   качался от TCP-пачек viiper и сам портил ритм.
2. **Стартовый заряд: 8 отчётов подряд** («V5 arms its native media writer
   with eight complete reports») — заполняет резерв контроллера.
3. ГЛАВНОЕ: **Windows HID не показывает кредиты L2CAP, завершения записей
   приходят пачками с засухами 39–82 мс**. Референс держит 8–32 отчёта «в
   полёте» (pinned OVERLAPPED-слоты, строго по кольцу). Наша синхронная запись
   HidSharp.Write глохла в засухи → контроллер голодал → Opus-декодер щёлкал.
4. **Собственная нумерация sequence** (старший ниббл байта 1) — контроллер не
   видит дыр в нумерации: внутренние потери не дают протокольных щелчков.

Реализация (`Output/BtMediaWriter.cs`):

- **BtMediaWriter** — отдельный overlapped-хэндл и кольцо из 8 закреплённых
  слотов (буфер+OVERLAPPED+событие); TrySubmit отправляет БЕЗ ожидания,
  Reap собирает завершения, WaitForSlot — строгий backpressure (новый отчёт
  не обгоняет старейший слот). Используется ТОЛЬКО для носителей 0x36.
- **CarrierPacer** — поток с абсолютной сеткой кадров 10,667 мс; очередь —
  HapticsChannel (FIFO 16, дедупликация пар 0x83+0x84, «немой» блок);
  при старте потока — заряд из 8 отчётов; каждый исходящий носитель
  перепрошивается своим sequence + пересчёт CRC (Resequence). Вся статистика
  видна в сводке «медиа-тракт: …» в окне программы.
- Слой контроллера (HidSharp, v1.9.1/v1.9.8) НЕ тронут: перечисление, открытие,
  ввод и отчёты состояния 0x31 — как раньше. Медиа-тракт открывается поверх
  уже выбранного устройства; при неудаче — прозрачный откат на прежний путь.
- Управление/вибрация/хаптики без аудио ведут себя как раньше.

Тесты: 137/137 (+7: перепрошивка seq с сохранением типа и валидным CRC,
кольцо 0..15, константы референса, целостность payload).

### v1.9.7 — РЕШЕНИЕ: мост замкнулся сам на себе через ВИРТУАЛЬНОЕ устройство; арбитр — caps коллекции + самоисцеление

Окончательный диагноз регресса v1.9.2 (по скриншотам пользователя):

1. В логе v1.9.6 видны ДВЕ противоположные коррекции транспорта за 2 мс
   (0x31/78: Usb→BT и 0x01/64: BT→Usb) — открытое устройство доставляет
   отчёты, НЕ СООТВЕТСТВУЮЩИЕ дескриптору своей коллекции. Так ведёт себя
   только ВИРТУАЛЬНОЕ usbip-устройство: viiper объявляет BT-форматные размеры
   (input 78/output 398 — чтобы игры могли писать хаптики 0x36), а фактически
   доставляет USB-форматные отчёты 0x01/64.
2. Улика-доказательство: в логе «Отдача от игры: моторы 192/255» — это ТОЧНО
   значения тестовой вибрации приложения (0xC0/0xFF). Тест записал вибрацию в
   открытое устройство (виртуальное), viiper вернул её как «отдачу от игры»,
   мост записал обратно — БЕСКОНЕЧНОЕ ЭХО. Мост bridging-овал виртуальное
   устройство с самим собой.
3. Почему v1.9.2 открыл виртуальное: v1.9.1 (HidSharp) при перечислении читал
   caps КАЖДОЙ коллекции теми самыми открытиями, которые висли на usbip — и
   устройство выбиралось по фактическим данным. v1.9.2 потерял и caps, и
   корректный отбор: цепочка предков (6 уровней) на реальной системе vHCI
   не достигала (глубже: HID→MI_xx→USB→порт→ROOT_HUB30→«ROOT\\USBIP_WIN2\\UDE»),
   а caps-классификация v1.9.4+ признавала виртуальное (78/398) «Bluetooth» —
   и оно выигрывало отбор у настоящего физического.
4. Дополнительно: классификатор «0x01 длиной 64 = USB» (написан по Linux-драйверу,
   где BT-минимальный отчёт ~10 Б) ошибочен для Windows — реальная BT-коллекция
   дополняет отчёты до 78 Б (подтверждено consolemode PR#132: «ReadFile may hand
   every report back padded to the size the HID descriptor declares»), поэтому
   минимальный BT-отчёт 0x01/64 легитимен и НЕ должен «переворачивать» транспорт.

Исправления:

- **Арбитр транспорта — caps СВОЕЙ коллекции**: ClassifyFromReport(report, inputCap):
  0x01 на 78-коллекции = минимальный BT (любая длина); 0x01 на 64-коллекции = USB;
  0x31/≥70 = BT. Транспорт больше не «переворачивается» на родных коллекциях.
- **САМОИСЦЕЛЕНИЕ (главное)**: AttachPhysicalDevice перебирает кандидатов;
  каждый открытый кандидат проходит ValidateLiveReports — отчёты обязаны
  соответствовать дескриптору своей коллекции (длина = InputReportByteLength).
  Отчёт «короче максимума» = почерк виртуального устройства → кандидат
  отвергается (в журнал пишется причина), блокируется на 60 с, берётся
  следующий. Даже если любой фильтр пропустит виртуальное — живые отчёты
  его выдадут, и мост гарантированно доходит до настоящего физического.
- **Цепочка предков: 6 → 12 уровней** (реальная глубина usbip-цепочки больше).
- **Команда --diagnose**: полный дамп одной командой — все DualSense-коллекции
  (путь, caps, цепочка предков, вердикт физический/виртуальный), HidHide
  (активность, белый список, список блокировки), viiper, и живые отчёты
  первого кандидата с проверкой согласованности.
- В логе подключения: «Пробую контроллер i/N: …» для каждого кандидата.

Тесты: 114/114 (+7: арбитр caps — 0x01/64 на BT-коллекции = Bluetooth;
подпись виртуального — отчёт короче caps; согласованность; fallback).

### v1.9.6 — ГЛАВНЫЙ регресс v1.9.2 найден: потерян отбор гейпадной HID-коллекции

По настоянию пользователя проведён полный аудит «что сломано в v1.9.2» (в
v1.9.1 всё работало). Найдена корневая потеря:

У DualSense НЕ ОДИН HID-интерфейс, а НЕСКОЛЬКО top-level коллекций (гейпадная
с отчётами input 78 Б (BT) / 64 Б (USB) + побочные — сенсорные и др., меньше).
Библиотека HidSharp при перечислении читала размеры отчётов КАЖДОЙ коллекции
(теми самыми открытиями, из-за которых оно висло на usbip-устройствах) — и код
v1.9.0–1.9.1 выбирал по ним ГЛАВНУЮ гейпадную коллекцию. Перечисление v1.9.2
«без открытий» эту информацию потеряло: MaxInput/MaxOutputReportLength стали
известны только ПОСЛЕ открытия, а выбор кандидата брал первую попавшуюся
коллекцию DualSense. Если первой шла ПОБОЧНАЯ — открытая «не та» коллекция
давала несовместимые размеры отчётов, инициализация падала, и мост считал
«контроллер не найден» → вибрации нет, тесты мертвы, игра же то работает с
физическим напрямую (курки!), то садится на виртуальный и теряет управление
(мост-то глухой). Этим объясняются ВСЕ симптомы v1.9.2–v1.9.5.

Исправление:

- **WinHidStream.ProbeCaps(path)** — чтение размеров отчётов коллекции через
  открытие с НУЛЕВЫМ доступом (только запрос дескриптора): не конфликтует с
  другими процессами и не может повесить приложение. Вызывается ТОЛЬКО для
  ФИЗИЧЕСКИХ кандидатов DualSense — виртуальные usbip исключены ранее по
  цепочке предков и не открываются ВООБЩЕ (свойство v1.9.2 сохранено: при
  работающей игре приложение не зависает).
- **EnumerateWithVirtuals** заполняет MaxInput/MaxOutputReportLength физ. кандидатов
  (как делал HidSharp) и уточняет транспорт по caps.
- **OrderPhysicalCandidates**: главная гейпадная коллекция (caps 78/64) —
  первой, затем BT раньше USB; побочные коллекции — в конце как запасные.
  BridgeService выбирает по этому порядку; в журнал пишется размер коллекции.
- Если открыта коллекция с несовпадающими размерами — явное предупреждение
  «возможно, ПОБОЧНАЯ коллекция» (раньше это было загадочное «транспорт
  остаётся …»).

Тесты: 107/107 (+3: порядок кандидатов — главная BT/USB впереди побочной BT,
BT раньше USB, fallback без caps).

- **Выбор кандидата: BT → USB → неопределённый** (раньше fallback брал

- **Транспорт по caps коллекции** (BT: input 78 Б; USB: input 64 Б) — уточняется

  отдельный СИНХРОННЫЙ хэндл (HidD_GetFeature не рассчитан на overlapped).
- **Overlapped-жизненный цикл**: ResetEvent перед каждой операцией; после

- **Проверка viiper**: корректный запрос «ping\0» вместо пустого подключения +

физические BT и USB; классификация транспорта по caps).

### v1.9.3 — «пропала вибрация, тесты не работают»: записи 0x31 не паддились до 398 Б

Симптом после v1.9.2: приложение больше не зависает, но вибрация в игре
пропала, тесты эффектов в приложении не работают; при этом курки (эффекты
триггеров) в игре работают.

Диагноз: Windows HID требует, чтобы WriteFile получал буфер РОВНО в
OutputReportByteLength — размер МАКСИМАЛЬНОГО output-отчёта коллекции.
BT-дескриптор DualSense объявляет серию отчётов 0x31=78 … 0x36=398 Б
(docs/RESEARCH.md), т.е. максимум BT-коллекции — 398 Б. WinHidStream v1.9.2
писал отчёт состояния 0x31 «как есть» (78 Б) — и КАЖДАЯ такая запись
отклонялась, вплоть до неудачи уже в Initialize (сброс подсветки) — физический
контроллер вообще не подключался к мосту. HidSharp (до v1.9.2) паддил нулями
до максимума автоматически (CommonWrite принимает maxOutputReportLength);
hidapi делает то же самое — поэтому раньше всё работало. Игра при этом могла
работать с физическим контроллером напрямую (он не скрыт, пока HidHide не
активен) — потому «курки работают», а хаптики (носитель 0x36 через мост) и
тесты — нет.

Исправления (`Core/Hid/WinHid.cs`):

- **PrepareWriteBuffer(report, outputCap)** — буфер записи дополняется нулями
  до OutputCap (398 Б для BT-коллекции); отчёт больше максимума — внятное
  исключение; неизвестный cap — запись как есть. Write() теперь пишет только
  подготовленный буфер.
- **ErrorIoPending: 996 → 997**. 996 — ERROR_IO_INCOMPLETE, ДРУГАЯ ошибка;
  ERROR_IO_PENDING = 997. Со старой константой любая операция, ушедшая в
  ожидание (на BT — почти каждая запись), ошибочно бросала исключение.
- В сообщения об ошибках Read/Write добавлен код ошибки Win32 (диагностика).

Тесты: 86/86 (+4: паддинг 78→398, точная длина, превышение, неизвестный cap).

### v1.9.2 — корень «не запускается при работающей игре»: перечисление HID открывало usbip-устройство

Симптом: v1.9.1 не помогла — если игра уже работает с DualSense-потоком,
приложение «не запускается от слова совсем».

удалён из проекта полностью:

- **Перечисление БЕЗ открытий устройств**: CM_Get_Device_Interface_List(PRESENT)

- **Ввод-вывод нативный**: WinHidStream = CreateFile(overlapped, share r/w) +

  застрявший запрос прерывается, вечное ожидание исключено); caps — из

- HidDeviceMonitor: вместо события HidSharp (которое требовало его probe с
  открытиями) — опрос перечня путей каждые 3 с (дёшево, безопасно).
- Порядок запуска: СНАЧАЛА мост, HidHide — потом и best-effort (проблемы

### v1.9.1 — запуск при уже работающей игре с DualSense-потоком

Симптом: если в фоне уже работает игра с DualSense-потоком (наш стек viiper
остался жить после аварийного завершения прошлой сессии), приложение «не

1. **Вечное зависание `usbip.exe --version`**: в GetInstalledUsbipVersion()

2. **Устройство прошлой сессии не переиспользовалось**: после падения приложения
   viiper-процесс и его виртуальный DualSense живут дальше, игра держит их.

3. **Тишина при неудачах**: 3 неудачи автозапуска подряд → окно программы
   показывается принудительно (раньше при StartMinimized пользователь не видел
   вообще ничего и не понимал, жив ли процесс).
4. ConnectAsync к viiper — таймаут 3 с (раньше мог висеть без ограничений).

Тесты: 74/74 (без изменений — правки в запуске/процессах, покрыто ручной
проверкой сценария «viiper жив + игра держит устройство»).

### v1.9.0 — контроль потока: контроллер больше не отваливается под нагрузкой хаптик

Симптомы v1.8.0 (журнал пользователя): при интенсивных хаптиках вибрация «стучит»,
управление отваливается, приложение зависает; в журнале цикл
«Физический контроллер отключён (DeviceIOException ... Failed to get info)» +
шторм ошибок записи.

Диагноз: поток 398-байтовых записей 0x36 на пределе возможностей BT-канала.
Когда канал не успевает — записи блокируются (таймаут 500 мс), очередь устройства
переполняется, Windows теряет контроллер (DeviceIOException), мост уходит в
карусель disconnect/reconnect (каждые 3 с — открытие, feature-чтения, инициализация),
каждая ошибка пишется в журнал/UI — приложение захлёбывается.

Реализовано (контроль потока — «пишем не быстрее, чем канал может»):

- **Адаптивный темп 0x36**: pace = max(10.5 мс, фактическая длительность записи ×1.25).
  Канал медленнее потока → пишем реже, излишек уходит через leaky-queue.
- **Деградация**: запись дольше 30 мс + очередь копится → пишем через блок
  (DropOldest, счётчик «деградация» в статистике), канал тонет — теряем часть
  хаптик, но НЕ срываем связь. Восстановление — автоматически (запись <20 мс).
- **Раздельные хэндлы HID**: чтение ввода и запись output-отчётов на РАЗНЫХ
  хэндлах устройства — заблокировавшаяся запись больше не останавливает ввод
  («управление отваливается» устранено структурно). Feature-отчёты — тоже
  через хэндл записи. Таймаут записи 250 мс (было 500).
- **Антишторм ошибок**: WriteFailed не чаще 1/5 с (шторм ошибок больше не
  заливает журнал и UI); «смерть» канала — 8 ошибок подряд; DetachPhysical
  не чаще 1/8 с; переподключение раз в 5 с.
- «Немой» блок не пишется при перегруженном канале (EMA ≥15 мс).

Тесты: 74/74 (адаптивный темп по таблице, условия деградации, DropOldest).

### v1.8.0 — допилка протокола: 1-мс таймер, дорожки 0x84/0x83, состояние в каждом кадре, усиление

Симптомы v1.7.0 (по статистике пользователя: «интервал записи 692 мс» при норме
~10 мс): вибрация появилась, но «не вся»; триггеры «иногда пропадают».

Три найденные причины:

1. **Таймер Windows 15,6 мс**: Task.Delay физически не мог выдержать темп
   10,5 мс — блоки писались в ~1,5 раза реже, очередь переполнялась, leaky-queue
   теряла треть блоков → вибрация «не вся». Решение: timeBeginPeriod(1) на всё
   время работы писателя (стандартная практика DS4Windows/игр).
2. **Потеря состояния в «тихих» кадрах**: с дуплекс-устройством viiper шлёт
   кадры с носителем ВСЕГДА; при тишине код делал ранний return — изменения
   триггеров/LED, приехавшие в таких кадрах, терялись. Решение: ранний return
   убран — состояние обрабатывается КАЖДЫМ кадром (0x31 пишется, когда очередь
   0x36 пуста).
3. **Гипер-дедупликация ровного тона**: одинаковые ПОДРЯД блоки (ровная
   вибрация) отбрасывались как «дубликаты 0x83+0x84» → хаптика с 50%-й скважностью.
   Решение двухуровневое: (а) дедупликация только в окне 8 мс (пары кадров
   приходят вплотную; реальные интервалы 10+ мс); (б) выбор дорожки — 0x84
   (realtime) приоритетен, 0x83 берётся только если 0x84 не приходит 500 мс.

Дополнительно:

- окно 250 мс для hapticsActive убрано (задерживало 0x31 до 250 мс после
  окончания хаптик) — теперь ориентир только очередь;
- **усиление хаптик** (слайдер 25..400%, по умолчанию 100%): множитель амплитуды
  PCM S8 с клампом, CRC пересчитывается — если игра шлёт тихие хаптики;
- статистика дополнена строкой «хаптики: записано/принято/дублей/отброшено»;
- ёмкость джиттер-буфера 16 блоков (~170 мс).

Тесты: 65/65 (окно дедупликации, ровный тон, усиление с клампом + CRC).

### v1.6.1 — починка дуплекса: кадры 0x84, пропуск тишины, темп ≤100 Гц

Симптомы v1.6.0: контроллер не работает в игре, программа «захлёбывается».

Причины (найдены в исходниках viiper v0.1.2 + PR potpiemuncher/Thrum #83):

1. **Кадры 0x84 «realtime haptics» выбрасывались**: v0.1.2 шлёт хаптики отдельным
   типом кадра 0x84 (474 Б, те же поля) на часах 93,75 Гц — наш клиент знал только
   0x81/0x83/0x85 и молча пропускал 0x84 (примечание Thrum: «Two new server→client
   frame types (0x84 realtime haptics, 0x85 mic interface state)»).
2. **Заливание BT-канала тишиною**: с дуплекс-устройством viiper шлёт кадры с
   носителем 0x36 на часах 0x83=100 Гц + 0x84=93,75 Гц ДАЖЕ КОГДА ИГРА МОЛЧИТ.
   v1.6.0 писал КАЖДЫЙ носитель (до 250 Гц × 398 Б) — канал захлёбывался,
   input-отчёты контроллера задерживались → «контроллер не работает».
3. Разбор носителя 0x36 (v0.1.2 bthaptics.go): состояние [13..75] (первые 47 =
   общий блок), ХАПТИКИ PCM [78..141] (64 Б, S8 стерео 3 кГц — «вибрация»),
   ОПУС-ДИНАМИК [142..143 заголовок 0x93+длина, 144..343 данные], CRC32
   (seed 0xEADA2D49, zlib-инкрементальный) в [394..397]. Хаптики и динамик —
   ДВЕ РАЗНЫЕ дорожки: «вибрация» = задние каналы PCM, динамик = Opus.

Реализовано:

- Клиент обрабатывает **0x84** (payload 474 Б = та же отдача).
- **Тишина не пишется**: носитель записывается только если блок хаптик [78..141]
  ненулевой ИЛИ Opus-динамик непуст — иначе обычный путь 0x31 (со слиянием).
- **Темп 0x36 ≤ 100 Гц** (MinRawInterval 10 мс; нативные часы хаптик 93,75 Гц) +
  newest-wins (свежий 0x84 вытесняет 0x83).
- **Патч состояния внутри 0x36** с пересчётом CRC (seed 0xEADA2D49): санитарная
  обработка триггеров, флаги совместимости, «игрок 1», масштаб вибрации — теперь
  патчи работают и при активном аудиоканале (единый PatchStateBlock; починен
  баг двойного масштабирования вибрации из v1.6.0).
- Журнал отдачи — не чаще 2 строк/с (при ~200 кадрах/с).

Тесты: 58/58 (тишина носителя, патч+CRC 0x36, 0x84 round-trip, лимит журнала).

   шлёт USB-отчёты напрямую). Наш виртуальный контроллер был
   `dualsensegamepadv5` — БЕЗ аудио-интерфейсов: игре просто некуда было писать
   хаптики, поэтому «вибрация не работает». Триггеры при этом идут обычным
   HID-отчётом 0x02 — потому и работали.
2. **BT-канал ~125 Гц** (опрос DualSense по BT ~8 мс): раздельные отчёты игры
   (триггеры/вибрация/подсветка по отдельности, несколько за кадр) переполняют
   канал → часть записей теряется → «сигнал пропускает» при быстрой стрельбе.

Реализовано:

- **Полный дуплекс (главное)**: виртуальное устройство теперь создаётся типа
  `dualsensecombinedaudioduplexv5` (аудио-интерфейсы: хаптики OUT + микрофон IN)
  с опцией `deviceSpecific.hapticsConverter:"sony-bt-wdl-sinc64-v1"` (sinc
  48→3 кГц; в viiper v0.1.2 опция игнорируется — используется базовый box16,
  тип и строитель 0x36 в v0.1.2 ЕСТЬ — проверено по тегу). Путь: PCM игры →
  viiper (ресемплинг) → кадр 0x83 → комбинированный BT-отчёт 0x36 (398 Б,
  состояние+хаптики) → запись как есть в физический контроллер. Фолбэк: если
  дуплекс не принят сервером — повтор с `dualsensegamepadv5`.
  Галочка «Полный дуплекс» в настройках (по умолчанию вкл).
- **Слияние команд** `OutputMerger`: кумулятивное состояние по ГРУППАМ полей
  (как mergeRawOutputReport viiper): раздельные команды игры склеиваются в
  одну плотную запись; флаг — секция обновляется, без флага — не трогается;
  флаг+нулевые данные = явное выключение. Поддержан селектор «vibration v2»
  (flag2.0x04 — kernel COMPATIBLE_VIBRATION2).
- **Адаптивный темп записи**: EMA фактической длительности записи ограничивает
  частоту (канал хуже — темп падает сразу, лучше — восстанавливается осторожно);
  **изменение блока триггеров — срочное** (отправка без ожидания интервала):
  быстрая стрельба больше не «проваливается».
- **Стабильность**: usbip.exe БОЛЬШЕ не запускается на потоке UI (кэш статуса
  зависимостей, фоновое обновление); UpdateTray маршалится в UI-поток
  (StatusChanged приходит из фоновых потоков); подключение контроллера в
  тестах — в фоне; глобальные обработчики исключений (UI/домен/фоновые задачи)
  пишут в журнал вместо вылета.

Тесты: 54/54 (6 новых: слияние раздельных команд, явный Off триггера,
vibration v2, независимые LED/RGB, сброс, патчи поверх слияния).

### v1.5.0 — «всё-всё с виртуального DualSense»: патчи совместимости, аудиоканал 0x36, диагностика отдачи

Симптомы (проверка в игре): ввод работает, но адаптивные триггеры/подсветка от игры

1. **Наш 47-байтовый общий блок точен**: static_assert(sizeof(dualsense_output_report_common) == 47)

   +10/+21, player_leds +43, RGB +44..46). Запись в контроллер корректна (тесты работают).
2. **viiper ([28..75] = точная команда игры)**: RawOutputReport = сам 48-байтовый USB-отчёт,

   Игра/Steam зажгла на виртуальном контроллере рисунок слота 2 — и мы его честно переслали.
4. **Аудиоканал**: BT-дескриптор DualSense объявляет output-отчёт **0x36 размером ровно 398 Б**

Реализовано:

- **Патчи совместимости** в FeedbackTranslator (игра пишет данные, но не выставляет флаги

- **Слияние структурированных полей viiper** в нативный блок, если игра их не прислала.
- **«Player LED: всегда игрок 1»** (по умолчанию вкл, галочка в настройках): любой рисунок
  заменяется на канонический P1=0x04 (kernel BIT(2)).
- **Аудиоканал 0x36**: BluetoothHidWriter.EnqueueRaw + BridgeService.OnFeedback — при
  заполненном носителе 398-байтовый отчёт пишется в контроллер напрямую (только BT);
  на USB — предупреждение в журнал (один раз).
- **Диагностика отдачи** FeedbackMonitor: каждое ИЗМЕНЕНИЕ состояния эффектов — строка
  Info в журнал (флаги/моторы/режимы триггеров/RGB/playerLED/аудиоканал), без спама;
  в окне новая строка «Отдача от игры: #N, <сводка>» — сразу видно, ЧТО игра шлёт.

Тесты: 48/48 (12 новых: патчи флагов, форсирование игрока 1, слияние полей, детекция 0x36,
монитор отдачи, канонические рисунки LED по kernel).

### v1.4.0 — «Multiple instances of vHci device interface found»: ghost-устройства vHci

Симптом (журнал пользователя v1.3.1, строки самого viiper): драйвер 0.9.7.7 уже
установлен, viiper запускается, но падает с

```
usbip-win2 0.9.7.7 driver/CLI probe failed: exit status 1:
error: Multiple instances of vHci device interface found.
```

Причина (найдена в интернете, PR qiin2333/sunshine-control-panel #115 + libusbip):
при замене usbip-win2 (наш случай 0.9.8.1 → 0.9.7.7) в системе остаётся
«ghost»-устройство виртуального USB-хост-контроллера (vHci); когда активных
(PRESENT) vHci-интерфейсов больше одного, ЛЮБОЙ вызов usbip.exe завершается этой
ошибкой. Деинсталлятор Inno очищает их не всегда, установщик новые не подчищает.

Реализовано (та же механика, что у usbip.exe / libusbip):

- `DriverSetup.GetVhciDeviceInstanceIds()` — перечисление АКТИВНЫХ vHci-интерфейсов
  через `CM_Get_Device_Interface_List(PRESENT)` (cfgmgr32, P/Invoke) по GUID
  {B4030C06-DC5F-4FCC-87EB-E5515A0935C0} — тот же GUID и флаг, которыми пользуется
  usbip.exe; instance ID извлекается из символьной ссылки (\?\root#usbip#0000#{GUID});
- `RemoveVhciDevices()` — elevated-удаление устройств `pnputil /remove-device`
  (один UAC на весь список);
- «Готовность» usbip (`IsUsbipReady`) теперь требует: версия == 0.9.7.7 И активных
  vHci ≤ 1 — раньше дубликаты не проверялись и считались «готово»;
- кнопка «Установить зависимости» при дубликатах: удаление всех vHci (sweep) →
  установка 0.9.7.7 → контрольная проверка (версия + число vHci) → требование
  перезагрузки (замена драйвера в ядре);
- диагностика: `--check-deps`, окно и диалог установки показывают число активных
  vHci и предупреждение при >1.

### v1.2.1 — viiper.exe запускался без аргументов и сразу завершался

### v1.0.1 — «программа не видит контроллер»

Симптомы (скриншоты пользователя): Windows видит DualSense по Bluetooth,
но в окне программы «Физический контроллер: не подключён», тесты эффектов выдают
`[WARN] Тест не выполнен: физический контроллер не подключён`, VIIPER-сервер «не подключён».

Причины и исправления:

1. **Определение транспорта (критично)**: транспорт искали по подстроке «bthhid»
   в пути устройства — на Windows пути HID имеют вид `\\?\hid#vid_054c&pid_0ce6&col_01#…`
   и признак шины не содержат, поэтому **любой BT-контроллер считался USB**:
   отчёты уходили в формате 0x02/48 Б вместо 0x31/78 Б (контроллер их игнорирует),
   feature 0x05 не читался (контроллер оставался в минимальном режиме).
   Исправлено: классификация по дескриптору (`GetMaxInputReportLength()` = 78 → BT,
   64 → USB; метод включает байт Report ID — документация HidSharp) + **уточнение
   в рантайме по первому input-отчёту** (`ClassifyFromReport`: 0x31/78 → BT,
   0x01/10 → BT-минимальный, 0x01/64 → USB) + самокоррекция при каждом Read().
   Покрыто юнит-тестами (`ClassifyFromReport_*`).
2. **Тесты и статус зависели от запущенного моста**: без VIIPER (зависимости не
   установлены) мост не стартовал → статус всегда «не подключён», тесты отказывали.
   Исправлено: тесты сами находят и открывают контроллер (`AttachPhysicalDevice`
   работает без моста); окно сканирует устройства независимо (раз в 2 с) и
   показывает «виден: DualSense [Bluetooth] — мост не запущен».
3. **Одноразовый автозапуск**: если viiper.exe только стартовал (порт ещё не
   слушается) или зависимости установлены позже, мост больше не пытался
   запуститься. Исправлено: супервизор повторяет каждые 15 с; ping VIIPER
   повторяется 5 раз с интервалом 2 с.
4. **UX зависимостей**: в окно добавлены строка «Зависимости (usbip+viiper)»,
   кнопки «Установить зависимости…», «Проверить», «Открыть журнал» (и в меню трея);
   `--list-devices` при отсутствии DualSense печатает все HID-устройства и причины
   (HidHide-скрытие, эксклюзивный захват, отсутствие сопряжения).
5. Мелочи: убрана утечка потока HidStream при attach (`TryOpen(out _)` перед
   открытием), писатель очереди корректно пересоздаётся при переподключении,
   устранён спам «DualSense не найден» при каждом изменении HID-устройств.

Тесты: 35/35 (было 31 — добавлены 5 на классификацию транспорта).
